# Проверки и критерии допуска

GearUP и взаимодействие с его приложением исключены из текущего плана по решению пользователя 24.09.2026.

Статус каждой фактически выполненной проверки хранится отдельно в [STATUS.md](STATUS.md). Этот файл — план, не свидетельство прохождения.

## Уровни доказательств

| Уровень | Что доказывает | Чего не доказывает |
|---|---|---|
| Unit / fault injection | Решения, порядок, обработку ошибок, generation | Сохранение TCP/UDP конкретным Xray |
| Реальный Xray на локальном стенде | Поведение точного binary/API и синтетических потоков | LAN TPROXY, реальные провайдеры, Keenetic offload |
| Роутер read-only | Фактическую версию и состояние в момент чтения | Безопасность обновления или горячей смены |
| Разрешённый аппаратный тест | Работу реального маршрута и ресурсный профиль | Выигрыш на любых играх/провайдерах |

## Этап 1a: планировщик

- Эквивалентный JSON с другим порядком полей → unchanged; порядок rules/outbounds/inbounds сохраняет смысл.
- Совпадение желаемого конфига и applied digest + identity + generation + свежий successful data-plane check → no-op.
- Ключ/файл тот же, но процесс другой, generation старый, health устарел/из будущего или отсутствует → verify; явный отказ → recover. Ни один случай не запускает restart.
- Одна/несколько изменённых outbounds → prepare outbound; rules/balancers → prepare routing; совместное изменение → prepare transaction.
- Listener/DNS/API/policy/неизвестное поле/domainStrategy/порядок default outbound → restart required для рассмотрения исполнителем.
- Структурно неверный JSON, duplicate/missing tags, NaN/Infinity → отклонение без вывода значений; аргументы не мутируют; результат не содержит секретов или полного config.

## Применение ключей и fault injection (1b–1d)

| Сценарий | Ожидаемое доказательство |
|---|---|
| Тот же здоровый ключ | Нет restart и побочных записей; передача данных продолжается |
| Тот же ключ, сломан runtime или загружен другой | Не ложный success/no-op; ограниченное восстановление |
| Меняется один Vless1/Vless2/VMess/Trojan/SS/HY2 | Независимые TCP+UDP потоки остальных протоколов продолжаются; изменяемый маршрут проверяется отдельно |
| Длинные TCP и UDP на старом поколении | Номера/байты до, во время и после перевода новых потоков; PID лишь дополнительная метрика |
| Неверный синтаксис, revoked/unreachable key, TCP-only кандидат | Старый рабочий runtime и маршрут сохраняются; UDP не отмечается рабочим по TCP |
| Ошибка add / rules / confirm / запись диска | Частичное состояние обнаружено; reverse operation или recovery; нет скрытого глобального restart |
| API исчез, завис, вернул ответ после deadline | Bounded timeout; stale response отклонён; неизвестный результат выясняется, а не дублируется |
| Одновременно manual, failover, подписка, route save | Один писатель; manual epoch побеждает старую работу; нет lost update |
| A→B→A, рестарт процесса с повторным PID | Старые evidence и post-apply результат не принимаются |
| Crash/reboot на каждой phase | Выбран согласованный snapshot; не остаётся вечной блокировки или неопределённого активного ключа |
| Удаление/drain старого outbound | Реально завершены старые потоки; RSS/heap/сокеты не растут с числом циклов |
| Режимы simple/advanced/web_only | Общий lock и корректное применение независимо от наличия пула/Telegram |

Стенд: собственные loopback TCP echo и UDP echo, синтетические конфиги без чужих endpoints. Для каждого потока последовательные номера и timestamp; стабильный контрольный поток параллельно изменяемому. Проверить стабильные новые маршруты и отсутствие пропуска правил/API-route. Снимать exit codes; все дочерние Xray/server/probe процессы завершаются в finally. HY2 — отдельный тест credentials/cache, не включать по результату VLESS.

Исследовать `rmo`/повторные поколения и `adrules append=false` с ошибкой в середине. Отдельно маршрутизация default и unknown destination, domain full/suffix/shared-IP, SOCKS candidate isolation, DNS/IPv6, UDP ASSOCIATE. Обнаруженная частичность API — блокирующий gate для production executor.

## Выбор маршрута (2–3)

| Сценарий | Ожидание |
|---|---|
| Direct лучше, разрешён политикой | Может рекомендоваться/выбираться после нескольких окон |
| Direct лучше, proxy-required | Исключён; отказ прокси не раскрывает direct |
| TCP работает, UDP нет | UDP-кандидат непригоден |
| Низкий median, плохой p95/jitter/loss/late | Не выигрывает автоматически у устойчивого кандидата |
| Мало данных, stale TTL, сменился сервер/WAN | «Нет данных» / повторное измерение; не 0% loss |
| Короткий всплеск vs устойчивое улучшение | Hysteresis/dwell не дают флаппинг; достаточное улучшение разрешает только новые сессии |
| Активная игра + новые voice/auth потоки | Профиль удерживает согласованный egress |
| Полный отказ | Разрешённый backup и явное возможное переподключение |
| WAN подписан A, фактически вышел B | Измерение отклоняется |
| Частые probes / мало RAM / занят CPU | Budget guard, один worker, отмена и cleanup, работающие сервисы сохраняются |

Loss измеряется нумерацией запросов и ответов к контролируемому узлу с заданным deadline, а не счётчиками conntrack. В отчёте нужны определение jitter, размер выборки, окно, server/destination identity, transport, WAN и возраст данных. Не считать HTTP time-to-response игровым ping.

Опора для реализации стенда: [RFC 1928](https://www.rfc-editor.org/rfc/rfc1928.html) — UDP ASSOCIATE и отсутствие пересылки ICMP средствами SOCKS; [RFC 8085](https://www.rfc-editor.org/rfc/rfc8085.html) — ограничения UDP-приложений и контроль нагрузки; [Linux TPROXY](https://docs.kernel.org/networking/tproxy.html) — socket support и policy routing. Они не подтверждают наличие нужных модулей в конкретной KeeneticOS: это отдельная аппаратная проверка.

## Нагрузка и сравнение

- Сначала сохранить датированный baseline с версией, process age, активными транспортами, характером нагрузки и свободным storage. Исторические baseline проекта использовать как контекст, не как контроль при иной нагрузке.
- CPU измерять разностью `/proc/stat` за интервал, RAM — RSS каждого процесса и MemAvailable; наблюдатель отдельно. После compilation/hash/probe сначала дождаться steady состояния.
- Последовательно idle → обычная нагрузка → применение → вся проверка пула → steady; одинаковая длительность и интервалы сравнения. Указать min/median/p95/max и число samples, рестарты, временные процессы, сокеты/conntrack и трафик probe.
- Для утечки нужны повторные циклы и тренд после drain, а не один высокий RSS. Если рост повторяем — ограниченный профиль heap/socket конкретного core с отдельным разрешением на необходимые перезапуски.
- Для сравнения маршрутов чередовать A/B/A/B на том же сервере игры, устройстве, WAN, времени/нагрузке насколько возможно; различать сетевой выигрыш и нагрузку ПК/декодирование. Один удачный запуск не доказывает причинность.

## GitHub update / rollback / update (1e)

1. До публикации: изменения этапа изолированы от прежних dirty файлов, regression suite, компиляция, shell syntax по каждому изменённому script, secret scan, UI smoke только если UI менялся. Версия/CHANGELOG согласованы; main SHA неизменяемая опора.
2. Перед обновлением: backup настроек и одной предыдущей версии, список хешей по прежнему SHA, свободное внутреннее место и baseline. Не выгружать секреты в отчёт.
3. Обновление штатным путём с GitHub. Привязать успех к marker **этой** операции; проверить hashes из нового SHA, один bot/Xray, web, Telegram, YouTube, DNS и фактические маршруты.
4. Проверить сохранность пулов/нескольких подписок/активных ключей/custom checks/режима. Новые данные после update защитить перед downgrade; snapshot rollback не обязан включать созданное позже.
5. Штатный rollback: восстановлены файлы старой версии и согласованные настройки; web/proxy/пулы работают. Для нового applied journal нужна совместимость или его явная безопасная миграция.
6. Повторный update: те же проверки; затем полный пул с resource budget. Временно неработающий кандидат не меняет активный ключ.
7. После здоровья: staging/archive и лишние backup удалены автоматически; осталась одна полная точка rollback. Проверить реальное освобождение UBIFS, а не только число каталогов.
8. Зафиксировать итоговый installed SHA, сравнение CPU/RAM/storage, оставшиеся риски и короткую память проекта. Суточный мониторинг не планируется.

## Блокирующие gates

- Не подтверждены API atomicity/rollback/drain или isolation транспорта → горячая смена этого транспорта выключена.
- Нет достоверного snapshot процесса → нет no-op по одному файлу/порту.
- Нет UDP/WAN измерения → соответствующий рейтинг неизвестен.
- Доступ и аппаратные циклы разрешены последним поручением пользователя; до них обязательны технические gates выше.
