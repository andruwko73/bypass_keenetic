# План реализации

Обновлён 24.09.2026. Пользователь подтвердил: «Фиксируем план и делаем всё в этом проходе». Разработка, публикация и аппаратные циклы обновления/отката авторизованы в пределах данного плана; повторно запрашивать доступ не требуется. GearUP полностью исключён: интеграция, установка, адаптер, взаимодействие с приложением на роутере и проверки совместимости. Собственные relay/multipath также вне объёма. Выполнение отмечается в STATUS.md; разрешение на релиз не отменяет критерии допуска.

## Инварианты

- Telegram, YouTube и другие назначения сохраняют назначенный маршрут; Vless1/Vless2 независимы логически при общем core.
- Pool probe не меняет активные ключи. Новый ручной выбор отменяет результаты фоновых операций, начатых до него. Подписка не удаляет чужие ключи/источники и не применяет устаревший результат.
- Один сериализованный владелец изменений runtime, конфига, ключей и firewall; очередь ограничена, задачи имеют generation и deadline.
- Выбор direct разрешается политикой назначения. При proxy-required отсутствие прокси не превращается в прямой маршрут.
- PID, открытый порт, сохранённый ключ, успешная временная проба и работа приложения — разные свидетельства.
- API только loopback, не web/LAN/WAN; локальные процессы всё равно входят в модель доверия.
- Секреты только в приватных файлах с ограниченными правами. Метрики/журналы/документы не содержат ключей, endpoints и подписок.
- Лимиты RAM/CPU, probe bandwidth, числа поколений и временных процессов обязательны; Python не обрабатывает каждый пакет.

## Первый небольшой этап: контракт планировщика

Новый `app/proxy_apply_plan.py` получает уже построенные текущую и желаемую конфигурации, а также доказательства текущего процесса. Он ничего не читает на роутере, не запускает процессы и не пишет файлы. Не включать его в manifests установщика до подключения production-пути.

Классификация: `unchanged`, `outbound`, `routing`, `outbound_and_routing`, `core`. Сравнение JSON сохраняет порядок массивов. Порядок/первый outbound консервативно считаются частью core: первый является default. Изменения `routing.domainStrategy` и прочих полей вне rules/balancers — core, поскольку изученный API их не применяет. Неизвестное поле не игнорируется.

Решение: подтверждённый `noop`; `verify_runtime`, если нет достоверной привязки; `recover_runtime`, если процесс/проверка явно не работают; `prepare_*` для подготовки ограниченной транзакции; `restart_required` для рассмотрения контролируемого перезапуска. Это **план**, не разрешение исполнителю. Ни одно решение не запускает restart само.

Для no-op нужны совпадение полного fingerprint applied config, того же process identity (boot id + PID + start ticks), актуального generation и свежий успешный data-plane check именно этого snapshot. SOCKS handshake или hash файла сами не создают evidence. Возврат к прежнему ключу не возвращает прежнее generation. В первом этапе evidence передаётся тестами; production collector относится к 1b.

Покрыть испорченную структуру, JSON NaN, изменение ключа без изменения tag, route order, default outbound, DNS/API/listener, stale/future health, PID reuse, generation race, отсутствие/отказ health, неизменность аргументов и отсутствие секретов в результате.

## Координатор и транзакция применения (1b–1d)

1. Получить общий межпроцессный lock в RAM; не иметь fallback без lock. Считать latest desired generation и manual epoch. Фоновая операция с прежним epoch прекращается.
2. Сформировать полный candidate config из snapshot ключей/маршрутов/настроек. Не менять постоянные ключевые файлы до подготовки. Проверить синтаксис точным бинарником и семантические ограничения.
3. Создать приватный атомарный checkpoint: исходное applied generation, цель, phase, обратные операции, expected process identity. Файл fsync + atomic replace; crash между каждым действием входит в тест.
4. Изолированно проверить кандидата с подтверждённым WAN и назначением. Не использовать health другого outbound. HY2 сохраняет одноключевую изоляцию до доказательства безопасности.
5. Добавить уникальный generation-tag без удаления рабочего outbound. Проверить существование и готовность. При частичной ошибке определить реальное состояние через API, не повторять вслепую.
6. Перевести **новые** потоки ограниченным подтверждённым способом. Сохранить API-route и все остальные назначения. Полный `ReloadRules` не считать атомарной транзакцией; не использовать до теста/обхода выявленной частичности.
7. Проверить нужный сервис в постоянном runtime. Под lock повторно проверить manual epoch/generation и process identity. При конфликте не записывать успех нового устаревшего состояния.
8. Согласовать durable config, ключевые файлы и applied marker. Порядок и recovery для runtime-success/disk-failure фиксируются до включения функции; на reboot выбран только один подтверждённый snapshot.
9. Старое поколение оставить для старых сессий. Drain должен учитывать реальную активность TCP и UDP, истечение/idle и общие соединения транспорта. Не называть таймер доказательством отсутствия потоков. При достижении лимита поколений отложить новую оптимизацию, а не рвать старые сессии молча.
10. Удалить только своё старое поколение после доказанного drain; проверить возврат ресурсов. Не считать `rmo` доказательством вызова Close или освобождения auth/mux cache.

Автоавария и плановая оптимизация имеют разные причины и допуски. При полном отказе допустим новый сеанс через разрешённого кандидата; обещать непрерывность старого нельзя. Любой общий restart получает явную причину и ограниченный сценарий, а не catch-all обработчик ошибки API.

## Модель измерений и выбора (2–3)

Ключ записи: `(device_profile, destination_profile, WAN, direct/proxy, protocol, key_identity, transport, test_kind, generation)`. Не складывать разные серверы/назначения в один рейтинг. WAN привязывать фактически — интерфейсом/mark/routing table, с проверкой egress, а не одним названием.

Порядок решения:

1. Capability: нужный TCP/UDP, рабочий SOCKS UDP ASSOCIATE, разрешённый WAN и MTU.
2. Политика: direct_allowed/proxy_required, исключения и принадлежность профилю.
3. Доступность и устойчивость: успешность, повторные и поздние отказы, свежесть и достаточность выборки.
4. Качество: median и p95 latency, определённая формула jitter, loss по нумерованным запросам/ответам контролируемого узла; late replies учитывать отдельно.
5. Решение: несколько окон, hysteresis, минимальное время на маршруте, cooldown, TTL и уверенность. 5 мс/10% не являются установленными порогами.

Разделять: HTTP/service availability; контролируемый UDP echo/probe; реальная метрика игры/приложения. ICMP ping не идёт через SOCKS сам по себе. HTTP Observatory не заменяет UDP. Отсутствующая метрика отображается «нет данных». Conntrack tx/rx не даёт loss; зашифрованный поток не раскрывает границу матча. Не посылать произвольные пакеты на игровые порты.

Начальный бюджет для будущего стенда: один probe worker, ограниченные timeout/байты/очередь; нагрузочный допуск уточнить измерениями. Не добавлять самостоятельный параллельный автопробер поверх существующего scheduler. Сначала выбранные пользователем профили устройств/назначений; обучение — отдельная итерация.

Связанные login/game/voice потоки закреплять за одним поколением/egress согласно профилю. Conntrack служит наблюдением, не командой миграции. Отдельный игровой core рассматривать только если выгода изоляции оправдает измеренный расход RAM/CPU.

## Границы текущего плана

GearUP не входит ни в разработку, ни в установку, ни в управление приложением, ни в отдельный тестовый контур. Сведения прежнего аудита остаются исторической справкой в ARCHITECTURE.md и не являются заданием на интеграцию. Свои relay/multipath, серверная инфраструктура и обязательное разделение общего Xray также не входят в эту итерацию.

## Выпуски и порядок допуска

- Выпуск A: достоверное applied state, общий координатор, подтверждённый no-op, проверенные способы смены ключей/маршрутов и восстановление. Диагностика API на локальном стенде предшествует включению. Протоколы/транспорты допускаются раздельно, включая Hysteria2; наличие дополнительного Trojan/Shadowsocks service проверяется отдельно. Первичное включение API может потребовать одного запланированного перезапуска при обновлении; обещание отсутствия перезапуска относится к последующим поддержанным операциям.
- Выпуск B: собственные профили устройств/назначений и диагностика direct/WAN/proxy с рекомендациями. Автоматического применения рекомендаций нет. Измерения доступны только при проверенном egress и пригодном измерительном endpoint; непроверенные UDP/WAN варианты не получают фиктивных показателей.
- Выпуск C: добровольно включаемый автоматический выбор для выбранных профилей после подтверждения качества B. Новые потоки направляются по новому выбору, связанные активные потоки закреплены; failover проверяется отдельно от оптимизации.

У каждого выпуска свой полный GitHub update → rollback → update. Между небольшими изменениями запускать только затронутые тесты; полный регрессионный набор и аппаратный цикл выполнять перед выпуском, повторять лишь при изменении, которое обесценивает результат, или после устранения ошибки.

## Конкретные условия завершения

1. На исходной версии восстановить сравнимый baseline и закрыть прежние шесть skipped там, где требуются Linux/symlinks/реальный Xray. Старые результаты не объявлять результатами нового кандидата.
2. Свести к одному coordinator web, Telegram, failover, подписки при затрагивании активного ключа, удаление ключа, маршруты, startup/recovery и endpoint repair. В каждом режиме проверить блокировки, exception cleanup и bounded deadlines.
3. Для каждой операции классификатор должен выдавать доказуемый no-op, ограниченный apply, восстановление либо обоснованную необходимость перезапуска. Неизвестное состояние требует проверки, а не скрытого restart.
4. На стенде подтвердить непрерывность независимых TCP/UDP и поведение старых поколений; fault injection охватывает API, файлы, исчерпание места, остановку исполнителя и reboot recovery. Проверить отсутствие direct fallback для proxy-required.
5. Ограничить очередь, число workers/поколений, размер истории и временные файлы. После повторных циклов проверить возврат памяти/сокетов/процессов; при устойчивом росте устранить причину до включения функции.
6. UI и бот показывают фактически применённое/неподтверждённое состояние, причину выбора, свежесть проверки и «нет данных». Секреты скрыты, существующие сценарии и режимы сохранены; для нового UI обязательны desktop/mobile и ошибки/задержанные ответы.
7. Для аппаратной проверки ориентир: 5–10 минут исходного покоя, 10–15 минут обычной нагрузки, ограниченная серия переключений, полная проверка всех пулов и 5–10 минут после завершения. Длительность уточняется по воспроизводимости; суточного наблюдения нет. Observer RSS и временные процессы считаются отдельно.
8. Критерии приёмки: у незатронутых контрольных потоков нет разрыва при поддержанной смене; неподтверждённый/плохой кандидат не становится активным; нет утечки по повторным сопоставимым циклам, лишних процессов и накопления файлов; обновление/откат/повторное обновление сохраняют рабочие сервисы и данные.

## Релизный порядок после допуска

Использовать `main`, version files и CHANGELOG; теги и карточки Releases не создавать без нового запроса. Зафиксировать immutable before/after SHA, проверить установленный файл по этим SHA. На роутере: baseline → update с GitHub → функциональные/ресурсные проверки → rollback → повторный update → полная проверка пула с нагрузкой → steady замер после выхода наблюдателей/компиляции. Подписки, маршруты, активные ключи, custom checks, режим и авторизация сохраняются. На внутренней памяти остаются программа и одна полная предыдущая версия; staging очищается только после подтверждения здоровья.
